Compiler · Fix 03

Resolved enum payload size

Intended behavior and failure

An enum stores a tag identifying its variant plus enough space for that variant’s payload. Planning and writing that payload must agree on its byte size. The old AST-based calculation could underestimate an object containing another object.

Reading the code

Option is Rust’s explicit maybe-value: Some(value) or None. HashMap maps names to resolved byte sizes. & borrows without taking ownership; ? on an Option returns None early when a lookup is absent. div_ceil(8) rounds bytes up to eight-byte words. with_type_universe supplies the already resolved sizes; object_words uses them when available instead of counting the source-level fields.

Why the correction works and how it was checked

A nested Receipt required 32 bytes while planning reserved 16 bytes. The corrected planner uses the same resolved size as object emission. Missing resolved sizes remain boxed (stored through a handle), rather than authorizing undersized inline storage. Planner regressions cover nested size, unknown size and threshold crossing.
